# rl/poker/ ポーカー AI の学習（CFR・CPU）

ヘッズアップ（1 対 1）ノーリミット・テキサスホールデム。ルールは [games/poker/](../../games/poker/)、
API は [apps/poker/](../../apps/poker/README.md)。GPU は使わない。

## なぜテトリスやオセロと作りが違うのか

このリポジトリのほかのゲームは**盤面が全部見える**ので、「この局面の価値」を学べばよかった
（テトリスとブロブチェインは DQN 系、オセロは n-tuple + TD、将棋は方策と価値のネット）。
ポーカーは**相手の手札が見えない**ので、同じやり方が通じない。

- 決まった打ち方は必ず読まれる。**手を確率で混ぜる**必要がある。
- 価値を学ぶ自己対戦（DQN・TD）は**収束しない**。じゃんけんと同じで
  「グー偏重 → パー偏重 → チョキ偏重」と巡回するだけになる。

そこで **CFR（Counterfactual Regret Minimization）**を使う。
「あの場面でこの手を選んでいれば、どれだけ得だったか」という**後悔**をためていき、
後悔の大きい手を選ぶ確率を上げる。平均戦略はナッシュ均衡に近づく。

ヘッズアップのゼロサムでは、均衡に近い戦略は**どんな相手に対しても期待値で負けない**。
これが「簡単に退場しない強さ」の正体で、運が悪い日はあっても、長い目で見てカモにされない。

## 先に小さなポーカーで確かめる

本物のホールデムは大きすぎて「本当に均衡に近づいたか」を直接は確かめられない。
そこで**答えが分かっている小さなポーカー**で実装の正しさを先に裏取りしている（`tests/poker/test_cfr.py`）。

- クーンポーカー（カード 3 枚）: 理論上の均衡を入れると **exploitability が 0**、
  先手の期待値がちょうど **-1/18**。測り方そのものが正しいことの確認になる。
- CFR+ を回すと、クーンポーカーは 2000 反復で 4.4e-5、Leduc ホールデムは 400 反復で
  0.0013 まで搾取されやすさが下がる。

> 実装したとき、**1 回の反復の途中で戦略が変わってしまう**バグを入れていた。同じ情報集合の
> 別々の局面が違う戦略で計算され、収束が 1/√T（素の CFR 相当）まで落ちていた。
> 走査の間は戦略を固定し、後悔の増分は最後にまとめて足すよう直したら、Leduc の
> 搾取されやすさが 26 分の 1 になった（しかも 2 倍速くなった）。`cfr.py` の `_Pass` 参照。

## 本物のホールデムをどう「まとめる」か

ノーリミットの局面は 10^160 通りある。そのままでは表に載らないので 2 方向にまとめる。

**ベット額** （`games/poker/rules.py` の `RAISE_FRACTIONS`）
フォールド / チェック・コール / ポットの 0.5 倍 / ポットの 1 倍 / オールイン の 5 つだけ。
人は任意の額を賭けられるが、AI に渡すときは一番近い枠に読み替える（アクション変換）。
倍率を 1 つ増やすと情報集合が約 1.8 倍になるので、学習時間との兼ね合いで 2 つにしてある。

**手札とボード** （`abstraction.py`）
- プリフロップは 169 通り（AA・AKs・AKo …）をそのまま使う。
- フロップ以降は「**このボードで相手が持ちうる手のうち何 % に勝っているか**」を 8 段階に分け、
  さらに「フラッシュを引きかけ」「ストレートを引きかけ」を別扱いにする（4 種類 × 8 = 32）。

ここは一度作り直している。最初は「役の絶対的な強さが全体の何 % か」で測っていたが、
それだと **A K Q のボードで 2 3 を持っている（ほぼ最弱）のに「A ハイだから中くらい」**になった。
相手が持ちうる手と比べる形に変えて解決した。全部（1225 通り）調べると遅すぎるので、
**ボードから決まる乱数**で選んだ 24 通りの見本と比べる。種がボードだけで決まるので、
同じ局面はいつでも必ず同じバケツになる（ぶれると学習が無駄になる）。

**スタックの深さ**
同じ手札でも、スタックが浅いと打ち方は全く変わる（浅いほど降りるか突っ込むかになる）。
10・20・35・50・75・100BB の 6 段階を別々に学習する。**退場が起きるのは浅いところだけ**なので、
浅い方を細かく刻んでいる。

## 学習する

```powershell
cd backend
.\.venv\Scripts\python -m rl.poker.train --run-name v1 --depth 5           # 100BB だけ
.\.venv\Scripts\python -m rl.poker.train --run-name v1 --resume            # 続きから
.\.venv\Scripts\python -m rl.poker.train --help
```

情報集合の鍵は先頭が深さの番号なので、**深さごとに表が完全に分かれている**。
6 つの深さを別プロセスで同時に走らせれば、そのまま台数分速くなる。

```powershell
# 6 プロセスで同時に走らせる例（PowerShell）
0..5 | ForEach-Object { Start-Process -NoNewWindow .\.venv\Scripts\python.exe `
  "-m rl.poker.train --run-name v1-d$_ --depth $_ --traversals 20000000" }
# 終わったら 1 つの戦略ファイルにまとめる
.\.venv\Scripts\python -m rl.poker.merge --out runs/poker/v1/checkpoints/best.npz `
  runs/poker/v1-d0/checkpoints/best.npz runs/poker/v1-d1/checkpoints/best.npz # …
```

i7-11700F で 1 プロセス約 350 回/秒、6 プロセス同時なら合計 750〜1500 回/秒
（浅い深さほど木が小さいので速い）。`runs/poker/<名前>/` に
config.json / metrics.jsonl / evals.jsonl / status.json / checkpoints/ を書く。
`python manage.py sync_runs` で `/poker/stats` に出る。

## 強さの測り方

ポーカーは運の幅が大きく、素朴に対戦させると 1 万局打っても差が見えない。そこで
**同じカードを配って席を入れ替えて 2 回打つ**（ミラー方式）。カードの運が打ち消し合う。

単位は **mbb/hand**（1 局あたりビッグブラインドの 1/1000 が何個か）。+50 でかなり勝っている。

「簡単に退場しないか」は別に測る（`evaluate.survival`）。スタックを持ち越して片方が
尽きるまで打ち、自分が尽きた割合を見る。

## 気をつけること

- **`config.py` のまとめ方を変えたら `ABSTRACTION_VERSION` を上げる**
  （テトリスの `FEATURE_VERSION`、オセロの `PATTERN_VERSION` と同じ）。古い戦略は使えなくなる。
- レイズ額の枠は `games/poker/rules.py` に 1 つだけ置く。学習側と画面側で別々に持つと、
  **学習していない手を AI に打たせる**事故になる（`tests/poker/test_learning.py` で縛ってある）。
- 学習した戦略が**まだ知らない場面**ではルールベースに任せる（`players.strategy_player`
  の `fallback`）。等確率にすると「ときどき急にでたらめを打つ AI」になり、一番弱く見える。
- 情報集合の鍵に**相手の手札を入れてはいけない**（カンニングになる）。
  `tests/poker/test_learning.py` の「情報集合の鍵に相手の手札が入っていない」で縛ってある。

## この先

- 抽象化を細かくする（バケツを増やす・レイズ倍率を増やす）。時間と引き換えに強くなる。
- **Deep CFR**: バケツで分けるのをやめ、局面をそのままニューラルネットに入れて後悔を予想する。
  まとめによる取りこぼしがなくなるが、学習はずっと重い。`mccfr.py` の走査の形はそのまま使える
  （後悔をためる先を表からネットに替える）。
- 3 人以上の卓。均衡の保証は消えるが、Pluribus と同じ考え方で「だいたい強い」ものは作れる。
