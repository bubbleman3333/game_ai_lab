# テトリス AI に「相手を見る目」を持たせる設計

**相手の盤面を見て守りと攻めを切り替える AI** の仕組み。土台（特徴量・報酬・API）は実装済みで、
`FEATURE_VERSION 2` で学習すれば使える。**この特徴量で学習した重みはまだ無い**ので、
学習するところが残っている。

関連: [backend/rl/tetris/README.md](../backend/rl/tetris/README.md)（学習の全体）、
[docs/TETRIS_RULES.md](TETRIS_RULES.md)（ルール）

## 何ができるようになるか

今の AI は**自分の盤面しか見ていない**（`rl/tetris/encoding.py` の 43 次元はすべて自分の情報）。
そのため次の 2 つができない。

- **守り**: 相手が大きい火力を溜めているから、今は高く積まずに低く構えておく
- **攻め**: 相手が高くて余裕がないから、今のうちに一気に畳みかけて倒しきる

この 2 つは別々の機能ではなく、**同じ 1 つの価値関数が両方向を学ぶ**。相手の状態が入力に入れば、
「相手が危ない局面の価値は高い」「相手が溜めている局面の価値は低い」として自然に表現される。

## いちばん大事な決定: 古いモデルを壊さない

特徴量を増やすと `FEATURE_VERSION` を上げることになるが、今の `load_checkpoint` は
バージョンが違うと**エラーにする**（`rl/tetris/model.py`）。このまま上げると、
`trial:best`（火力特化）も `v3-selfplay:best` も画面から消える。それは避ける。

**チェックポイントに入っている `feature_version` を見て、使うエンコーダを選ぶ**ようにする。

| チェックポイント | 入力 | エンコーダ |
|---|---|---|
| `feature_version: 1`（`trial` など） | 43 次元 | `encode_v1`（今のもの。変更しない） |
| `feature_version: 2`（これから作る） | 52 次元 | `encode_v2` |

- `encoding.py` に `encode_v1` / `encode_v2` を両方置き、`FEATURE_DIMS = {1: 43, 2: 52}` を持つ。
- `NeuralAgent` は読み込んだバージョンを覚え、自分のエンコーダを使う。
- `load_checkpoint` は「知らないバージョン」だけをエラーにする。
- 学習（`train.py`）は常に最新版で行う。

こうすれば**古いモデルと新しいモデルが同じ画面に並び、遊び比べられる**。
火力特化のモデルを残したいという方針（ブロブチェインの `versus` / `chain` と同じ）を守れる。

## 足す特徴量（9 個・43 → 52 次元）

相手の**置き場所を読むわけではない**ので、盤面をそのまま渡す必要はない。
「どれだけ追い詰められているか」「どれだけ殴り返してくるか」が分かれば足りる。

| 名前 | 中身 | 割る値 |
|---|---|---|
| `opp_present` | 相手の情報があるか（0 / 1） | 1 |
| `opp_max_height` | 相手の一番高い列 | 20 |
| `opp_agg_height` | 相手の高さの合計 | 200 |
| `opp_holes` | 相手の穴の数 | 20 |
| `opp_bumpiness` | 相手の凸凹 | 40 |
| `opp_pending` | 相手が抱えている保留おじゃま（段） | 20 |
| `opp_margin` | `20 - (opp_max_height + opp_pending)`。**あと何段で相手が死ぬか** | 20 |
| `opp_combo` | 相手の combo | 10 |
| `opp_b2b` | 相手の B2B（0 / 1） | 1 |

設計上のポイントが 3 つある。

**1. `opp_present` は必須。** これが無いと「相手がいない（ひとり遊び）」と「相手の盤面が空
（＝相手が絶好調）」を区別できない。1 つのモデルでひとり遊びと対戦の両方を扱うために要る。

**2. `opp_margin` は他の値から計算できるが、あえて直接入れる。** ここが「トドメを刺せるか」の
判断の中心になる非線形な量で、ネットに自力で見つけさせるより与えたほうが早い。

**3. `opp_pending` には「この手で送る分」を足す。** 候補手を評価するときの相手の状態は、
**その手を打った後**でなければならない。`LockOutcome.sent`（相殺後に相手へ送る段数）があるので、

```
opp_pending = 今の相手の保留 + c.outcome.sent
```

とする。これで「この手を打てば相手は受けきれずに死ぬ」が価値に直接あらわれる。
これが**畳みかけを学ぶための肝**。

### 見送るもの: 自分の「溜め」の大きさ

「次のターンに解き放てる火力の総量」を入れたいところだが、素直に作ると
候補手ごとに「その後の局面の候補手」を全部数えることになり **O(n²)** で重すぎる。
既にある `wells`（I 字穴の深さ）・`b2b`・`combo` がある程度代わりになるので、まずは入れない。
学習後に「溜めない／溜めすぎる」挙動が見えたら、そのとき考える。

## 局面の持ち方

`Position` に相手の情報を足す。**盤面そのものではなく、計算済みの数値**を持たせる
（相手の情報は候補手ごとに変わらないので、1 局面につき 1 回計算すれば済む）。

```python
@dataclass
class OpponentView:
    """相手の様子。盤面から一度だけ計算して持ち回る。"""
    max_height: int
    agg_height: int
    holes: int
    bumpiness: int
    pending: int      # 保留おじゃまの合計段数
    combo: int
    b2b: bool

    @classmethod
    def from_game(cls, g: Game) -> "OpponentView": ...
    @classmethod
    def from_dict(cls, d: dict) -> "OpponentView": ...   # rows から board_features() で作る

@dataclass
class Position:
    ...
    opponent: OpponentView | None = None   # None ならひとり遊び
```

`VersusEnv.position(side)` は相手側の `OpponentView` を入れて返す。

## 報酬に「勝ち」を足す

今の報酬は `生存 +0.1 / ライン +0.2 / 火力 +1.0 / 自分が死ぬ -5.0` で、
**相手が死んでも 0**。これでは「今トドメを刺す」と「後で同じだけ殴る」が同じ価値になり、
畳みかける動機が生まれない。`RewardConfig` に対になる項目を足す。

```python
win: float = 0.0   # 相手をトップアウトさせた（自己対戦のときだけ効く）。**既定は 0 = 使わない**
```

> 人間を相手に学習させる場合は勝敗を報酬に入れてはいけない（格下に勝てるので手を抜くことを
> 学んでしまう）。自己対戦では相手が常に同格なので、その問題は起きない。
> ただし**別の理由で、今の実装は使ってはいけない**（下）。

### 失敗: 勝ちをどの遷移に付けるかで壊れた

相手は**自分の手番**で死ぬので、こちらの手と時間がずれる。勝った側には終端の遷移が無いため、
対局が終わった時点で最後の局面に 1 つ流す実装にした。

```python
sink(prev[winner], cfg.reward.win, prev[winner], done=True)   # ← これが問題
```

**これは間違いだった。** 勝った側の「最後の局面」は勝ちと因果関係がない（相手が勝手に死んだとき、
たまたまそこにいただけ）。そこへ終端の +5 を教えると、**同じ盤面が「ふつうの局面」にも
「終端で +5 の局面」にもなり**、価値関数の辻褄が合わなくなる。負けの -5 は「自分の盤面が悪いから
死んだ」という因果があるので問題ないが、勝ちにはそれがない。

実測（`v5-opponent`）: 自己対戦に切り替わる ep 3,000 までは v3 を上回るペースだったのに、
切り替わった途端に崩れた。

| ep | ソロ ライン | おじゃま火力 | vs これまでの best |
|---|---|---|---|
| 3,000（自己対戦に切替） | 116 | **70** | — |
| 3,500 | 103 | 46 | 45% |
| 4,000 | 50 | 24 | 30% |
| 5,500 | 117 | 43 | 22% |

以降 5 回の評価で一度も `best.pt` を更新できなかった（＝ ep 3,000 の自分に勝てない）。
そのため **`win` の既定を 0 にした**。使いたいなら、終端に足すのではなく
**トドメの火力を出した手そのものの報酬に足す**形に作り直すこと。

## API とフロントの変更

**対局 API**（`apps/tetris_ai/serializers.py`）: `PositionSerializer` に `opponent` を足す。
**省略可**にして、無ければ `opp_present = 0`。これで古い呼び出しもそのまま動く。

```json
"opponent": { "rows": [...], "pending": [[3, 5]], "combo": -1, "b2b": false }
```

**同じ画面での対戦**（`frontend/src/games/tetris/game/versus.ts`）: 両方の盤面が手元にあるので、
そのまま渡せる。

**オンライン対戦**: 今は人と人しか戦わない（AI は入っていない）ので、**変更していない**。
将来オンラインに AI を出すときは、`opponent_state` に相手の `rows` と `pending` は既に入っているが
`combo` / `b2b` が無いので足すことになる。そのときは `protocol.py` と `protocol.ts` の
**両方を直すこと**（CLAUDE.md の決まり）。なお `state` は 5〜10 回/秒なので相手の盤面は少し古い。
人間も同じ条件で見ているので問題ない。

### 失敗例: `--selfplay-start 0` にしてはいけない

当初この文書には「相手を見る学習は自己対戦でしか起きないので `--selfplay-start` は早めに」と
書いていたが、**それで実際に失敗した**（`v4-opponent`）。

| ep 5,000〜5,500 | v3-selfplay（カリキュラムあり） | v4-opponent（`--selfplay-start 0`） |
|---|---|---|
| ソロ ライン | 116 | 95 |
| おじゃま火力 | 58 | **7** |
| vs ヒューリスティック | 100% | **5%** |

ライン消しは覚えたのに、**攻撃をまったく覚えなかった**。原因は鶏と卵で、
最初から自己対戦にすると弱い者同士なので誰も火力を出さず、殴られないので殴り返す必要がなく、
「シングルを消して安全に積み続ける」平和な均衡に落ち着いてしまう
（`play_versus_episode` はランダムおじゃまを一切降らせない）。

**`--selfplay-start` は既定の 3000 のままにして、まずランダムおじゃま（`garbage_end`）で
殴られながら攻撃を覚えさせること。** 最初の 3000 エピソードは相手の特徴量が 0 のままだが、
「攻撃を知らないまま最後まで行く」ほうがはるかに悪い。

自己対戦を最初から使いたいなら、`VersusEnv` にも弱いランダムおじゃまを混ぜる必要がある（未実装）。

## うまくいったと判断する材料

- `v3-selfplay:best`（相手を見ない自己対戦モデル。ep 7,500）と**直接対戦させて勝ち越すか**。
  これが本命の指標。`--versus-games` は 20 以上にすること（少ないと運で決まる）。

  ```powershell
  .\.venv\Scripts\python -m rl.tetris.evaluate runs/tetris/v5-opponent/checkpoints/best.pt `
      --vs runs/tetris/v3-selfplay/checkpoints/best.pt --vs-games 20
  ```
- おじゃまありの生存率が上がるか（`trial` は最後まで 0%、`v3-selfplay` は 30% まで届いた）。
- 相手が高いときに火力を出し惜しみしなくなるか（対局のログを見る）。
